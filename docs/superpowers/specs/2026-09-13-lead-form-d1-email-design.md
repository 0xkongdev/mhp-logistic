# Lead Form, D1 Storage, and Email Notification Design

## Goal

Turn the existing consultation form into a reliable lead-capture flow. A valid submission must be stored in Cloudflare D1 before the website reports success. The system then emails the lead details to `0xkong2610@gmail.com` through Resend without exposing credentials to the browser.

## Scope

This change covers the consultation form on the home page, a same-origin Cloudflare Worker API, one D1 database and migration, and one email notification per accepted lead. It does not add an admin dashboard, lead editing, user accounts, marketing automation, or Zalo integration.

## Architecture

The React form sends JSON to `POST /api/leads`. The existing Cloudflare Worker validates and normalizes the submission, inserts it into D1 with `email_status = 'pending'`, and returns an accepted response after the database write succeeds. Email delivery runs as a background task through `ExecutionContext.waitUntil()`. The task updates the row to `sent` with the provider message ID, or to `failed` with a short error description.

Database persistence is the source of truth. A Resend outage must never discard an otherwise valid lead or cause the visitor to resubmit unnecessarily.

## Data Model

The `leads` table contains:

- `id`: application-generated UUID primary key.
- `full_name`: trimmed visitor name, maximum 100 characters.
- `phone`: trimmed phone number as entered, maximum 30 characters.
- `need`: trimmed consultation/import need, maximum 500 characters.
- `source_path`: page path that submitted the lead, maximum 200 characters.
- `email_status`: `pending`, `sent`, or `failed`.
- `email_message_id`: nullable Resend message ID.
- `email_error`: nullable, bounded diagnostic message for operations.
- `created_at`: UTC timestamp generated by the Worker.
- `email_updated_at`: nullable UTC timestamp of the latest notification attempt.

An index on `created_at` supports reviewing recent leads. The system does not store visitor IP addresses.

## API Contract

`POST /api/leads` accepts:

```json
{
  "fullName": "Nguyen Van A",
  "phone": "0901234567",
  "need": "Nhap hang tu Trung Quoc",
  "sourcePath": "/",
  "website": ""
}
```

`website` is a honeypot field and must remain empty. All three visible fields are required. After removing common separators and an optional leading plus sign, the phone value must contain 8 to 15 digits. Unknown JSON fields are ignored.

Responses:

- `202`: the lead was stored and notification was queued.
- `400`: malformed JSON, failed validation, or a filled honeypot.
- `405`: unsupported method.
- `500`: the database write failed, so the lead was not accepted.

The API returns stable Vietnamese user-facing messages and does not expose database or email-provider errors.

## Frontend Behavior

The form uses controlled inputs with appropriate names and autocomplete hints. Submitting disables the button and shows a sending state. Field validation errors are shown accessibly without clearing entered values.

On a `202` response, the form clears and displays a success message stating that MHP will contact the visitor soon. Network and server failures display a retryable error. Repeated clicks are prevented while a request is active. No automatic retries are performed, avoiding accidental duplicate leads.

## Email Delivery

The Worker calls Resend's HTTPS API using a `RESEND_API_KEY` Cloudflare secret. The recipient is fixed server-side as `0xkong2610@gmail.com`; the browser cannot override it. The sender is configured through a non-secret `LEAD_EMAIL_FROM` environment value. Initial testing may use Resend's onboarding sender when the Resend account belongs to the recipient; production can switch to an address on a verified domain without code changes.

The plain-text and HTML email include the lead ID, name, clickable phone number, need, source page, and submission time in the Asia/Ho_Chi_Minh timezone. All visitor content is escaped before inclusion in HTML.

## Security and Abuse Controls

The Worker enforces content type, request-body size, field length, and phone validation. SQL uses bound prepared statements. Email HTML escapes all visitor-controlled text. The API is same-origin and does not enable permissive cross-origin access. The hidden honeypot rejects basic automated submissions without creating a lead.

Credentials never appear in source code, Wrangler configuration, client bundles, logs, or API responses. The Resend API key is stored only as a Cloudflare secret.

## Failure Handling and Operations

Database insertion is synchronous and mandatory. Email sending is asynchronous and best-effort after persistence. Failed email attempts remain visible in D1 through `email_status = 'failed'`; this version does not automatically retry them. Cloudflare Worker logs record the lead ID and provider result but not the full phone number or need text.

Deployment requires creating and binding a D1 database, applying the SQL migration locally and remotely, setting `RESEND_API_KEY`, and configuring `LEAD_EMAIL_FROM`. The recipient address is restricted in Worker code/configuration.

## Testing

Tests are written before production code and cover:

- Validation of required fields, lengths, phone formats, malformed JSON, and honeypot submissions.
- A valid API submission inserts exactly one normalized row and returns `202`.
- A D1 failure returns `500` and does not queue email.
- Successful and failed email tasks update the stored delivery status correctly.
- Email rendering escapes visitor-provided HTML.
- The React form sends the expected payload, prevents duplicate clicks, preserves values on failure, and clears values on success.

The final verification runs the focused tests, full test suite, linter, TypeScript build, and a local Worker smoke test against local D1. Live email delivery is verified only after the Resend secret is configured.
